# 【系统名称】需求规范

> 性质：**活文档**，单文件基线。条款写系统必须做到什么、怎么算通过。
> 状态：生效中（YYYY-MM-DD）
> 范围：【本期交付一句话，以及明确不作为对外稳定服务的能力。】
> 对外规格：未定版。定版时另存一份带版本号和日期的文件，本文件继续作活文档。

适用：需求条数少、共享口径不多、由一人维护。条数增多或要分用户侧 / 运营侧对外承诺时，按文末对照拆到成体系模板，已有编号保持不变。

交叉引用用编号（R4.5、E2、M2），不用「第 N 节」。编号只增不复用。作废的保留编号，状态改为「作废」。

可选小节没有内容就整节删掉，不留空标题。

## 1. 修改纪律

1. 新条款先写进本文件，对外规格保持「未纳入」。
2. 用户能单独提出的一件事用新的 R 编号（当前最大号 +1）。同一目标的细化用 `RNN.k`。
3. 两条以上需求共用的口径写在第 3–6 节，需求条目里只引用编号。
4. 现状快照可以写实现事实；需求表不可以。快照过期只说明未复核，不改变条款效力。
5. 定版另存新文件。定版稿删掉每条需求里的现状快照和实施分期，只保留承诺、验收、范围外和已知问题。

## 2. 用语、优先级、分期

### U1 强制程度

| 用语 | 含义 |
|------|------|
| **应** | 强制。未满足则对应条款不通过 |
| **宜** | 优先采用。有书面理由方可不用，并写明代偿 |
| **可** | 扩展。做了须符合同一套权限、审计和数据口径；不做不构成本期验收缺陷 |

### U2 优先级

| 优先级 | 含义 | 验收处理 |
|--------|------|----------|
| **P0** | 本期基本交付 | 未完成则不具备最终验收条件 |
| **P1** | 本期增强 | 未完成须书面确认并设整改期限 |
| **P2** | 后续扩展 | 本期只做预留和扩展验证 |

「内测」「试行」和 P2 不作为本期大规模对外稳定服务承诺。

### U3 分期叫法

| 叫法 | 指什么 | 不要写成 |
|------|--------|----------|
| **一期 / 二期 / 三期** | 建设分期 | 排期第一期 |
| **【实施分段名】** | 实施计划中的分段，不代替本期验收 | 建设一期 |

## 3. 术语

## 6. 范围边界

### B1 本期不做

本期不包含：【列表】。

只做预留、不要求完整上线的：【列表】。写在这里的事项，不得再写成任一需求的本期通过条件。

### B2 预留不得封闭

本期的模块边界、标识、权限和扩容预留，不得使下一期必须整体替换。未经书面授权不得用于外部训练；出域调用默认关闭。

## 13. 定版时保留什么

另存为 `需求规格说明书-{用户侧|运营侧}-V1.x-YYYY-MM-DD`。从本文件搬过去时：

| 保留并按受众重写 | 删除 |
|------------------|------|
| 需求表、验收、U/E/M/B 中已承诺的部分 | 现状快照 |
| 范围表（纳入 / 不纳入） | 实施分期和内部排期 |
| 范围外、已知问题口径、优先级 | 集合名、字段名、函数名、接口路径 |
| 术语里用户或运营需要的词 | 待办且本版不承诺的条款 |

未收编的编号保持「未纳入」，不得出现在定版正文里。
