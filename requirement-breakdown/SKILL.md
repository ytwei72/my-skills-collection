# 需求分解与需求规范编写

输入是一段话，输出是落进需求体系的条款。三个参数：

| 参数 | 取值 | 默认 |
|------|------|------|
| 原文 | 消息里的文字、附件，或用户给的文件路径（先读全） | 必需。没有就问，不要拿会话里的别的内容凑 |
| 存放路径 | 目录，或以 `.md` 结尾的单文件路径 | `docs/requirements`（项目专属说明另有约定时从其约定） |
| 模板 | 成体系 / 单文件 | 成体系。用户说「单文件」「一个文件」才用单文件 |

**模板来源**：项目里有 `docs/requirements/需求规范模板/` 就用项目的（项目可能改过）；没有就用本技能的 [templates/](templates/README.md)。下文「模板目录」指二者之一。成体系在 `模板目录/成体系/`，单文件是 `模板目录/单文件/需求规范.md`。写之前读一遍要用到的模板文件，按它的小节和注释填。

**项目专属说明**：仓库根下有 `.cursor/skills/requirement-breakdown.project.md` 时，开工前先读。它写的已有体系位置、文件对照、校验命令、定版方式，优先于本技能的默认做法。

## 红线

1. **条款写「系统必须做到什么、怎么算通过」。** 集合名、字段名、函数名、接口路径、技术选型不进需求条目，放现状快照或方案文档。口诀：交给不看代码的测试同学，能否照着判通过或不通过。
2. **不编造。** 原文没给的数值、角色、时限、范围，不写成条款。验收写可判定的定性结果，缺的数字列进「待确认」。
3. **编号只增不复用。** R 编号和子编号都是。作废的保留编号、标作废，不回收。
4. **交叉引用写编号并链到文件**（`[R5](./需求/R05-工单列表.md)`、R5.3、E2），不写「第 3 章」「§1.8」。
5. **跨需求共享的口径写进通用规格**，单条需求只引用编号，不复述。
6. **只写活文档。** 不动任何 `需求规格说明书/` 下的文件（含 .docx），新条款的对外规格一律「未纳入」。定版按项目专属说明，或按体系内 `需求规格说明书/README.md` 的步骤另行处理。

## 工作流

```
- [ ] 1. 定目标体系（读项目专属说明 + scan）
- [ ] 2. 分解原文
- [ ] 3. 对照现有需求定落点
- [ ] 4. 出分解清单，等确认
- [ ] 5. 写文件
- [ ] 6. 同步关联文件
- [ ] 7. 校验
- [ ] 8. 汇报
```

下文 `python` 指项目所用的解释器：项目用 uv 时写 `uv run python`。

### 1. 定目标体系

```powershell
python .cursor/skills/requirement-breakdown/scripts/req_tool.py scan <存放路径>
```

输出列出每套体系的总览、条目模板、下一个编号、每条需求的状态和背景摘要、通用规格编号。

| scan 结果 | 处理 |
|-----------|------|
| 一套成体系 | 在它上面增改。沿用它自己的总览文件名、条目模板、通用规格文件和编号前缀，不套模板默认名 |
| 一个单文件 | 在该文件里增改 |
| 多套 | 选与原文主题最贴近的；拿不准在第 4 步问 |
| 没有 | 按模板新建（第 5 步「新建体系」） |
| 已有体系的格式与用户要求的模板不同 | 不另起一套，在第 4 步说明并问是否迁移 |

已有体系可能改过名（例如用 `需求说明/` 代替 `需求分析/`、总览不叫 `总览.md`）。只要有台账标记和 `需求/RNN-*.md`，就是成体系，往里写，不要在旁边另建 `需求分析/`。

「新门类」指原文的用户目标在台账里找不到，做法是在同一体系里新建 R。只有存放路径下没有体系时，才新建一整套。

### 2. 分解原文

1. **拆句**：拆成原子陈述，一句只含一个主体和一个要求或事实。「并且 / 同时 / 以及 / 还要」连着的拆开。
2. **标类型**：功能、需求动机、业务规则、角色权限、对象状态、范围、非功能、界面、分析研究、测评结果、问题现象、排期、术语、实现细节。每类写到哪、怎么写，见 [reference.md](reference.md#内容类型与落点)。
3. **归组**：用户能单独提出的一件事是一条 R；同一目标下的细化是子编号。
4. **定强度**：强制程度用应 / 宜 / 可；优先级 P0–P2（已有体系用别的档位就沿用）。原文没说的按「核心闭环 P0、增强 P1、以后再做 P2」推定，清单里标「推定」。
5. **写验收**：可观察结果，带原文给的条件、数量、时限。

### 3. 对照现有需求定落点

先读台账和 scan 的背景摘要，再用原文关键词 Grep 需求目录和通用规格，命中的需求文件读全文。只看台账容易误判「已包含」，条款原文才是依据。对每条原子陈述判定：

| 判定 | 依据 | 动作 |
|------|------|------|
| 已包含 | 现有条款表达了同样要求，验收不弱于原文 | 不改，清单里写明对应子编号 |
| 细化 | 同一用户目标，原文更具体（多了阈值、场景、界面元素） | 改该子编号的需求或验收，或在该 R 追加子编号 |
| 交叉 | 同时牵涉两条及以上 R | 条款放进拥有这个用户目标的 R；另一条在「与相邻需求的分工」写边界；两条以上共用的口径进通用规格 |
| 冲突 | 与现有条款矛盾（数值、权限、范围、非目标不一致） | 不自行覆盖，第 4 步并列原条款与原文，由用户定 |
| 新门类 | 台账里找不到这个用户目标 | 新建 R，编号取 scan 给的下一个编号 |
| 不入需求 | 纯实现细节、个人倾向、与本系统无关 | 不写进条款；能归方案文档或现状快照的放那里 |

拿不准新建还是挂子编号时，挂子编号。开错的编号收不回。

### 4. 出分解清单，等确认

动文件前先给用户这张清单：

```markdown
**目标**：docs/requirements/需求分析/（已有成体系）。本次更新 R5、R2；新建 R12 需先解决 1 条冲突。

| # | 原文摘句 | 类型 | 判定 | 落点 | 拟写条款 |
|---|----------|------|------|------|----------|
| 1 | 工单列表能按处理人筛选 | 功能 | 细化 | R5 追加 R5.5 | 工单列表应可按处理人筛选，并可与 R5.4 叠加（P1 推定） |
| 2 | 每天 8 点推送工单日报到企业微信群 | 功能 | 冲突 | 确认后新建 R12 | 系统应每天 08:00 推送前一日工单汇总（P1 推定） |

**冲突**：R5「约束与说明」写明不承诺消息推送，原文要推日报，是否放开？
**待确认**：日报推送到哪些群、由谁配置；没有新工单的日子是否也发。
```

完整示例见 [reference.md](reference.md#分解示例)。

用户确认或纠正后再动手。用户事先说了「直接写」「不用确认」，且没有冲突、也不用新建一整套体系时，可以跳过等待，但清单仍放进最后的汇报。

### 5. 写文件

**新建一条需求（成体系）**

复制该体系的条目模板（scan 输出的「条目模板」）为 `需求/RNN-简短标题.md`（两位编号，标题与 frontmatter `title` 一致），删掉注释段，按小节填。没有内容的可选小节整节删除。

- `status`：默认待办。原文说明已实现、测评已通过时写已落地或部分落地，并写「现状快照（日期）」，日期取测评或说明里的日期。
- `priority`：未完成条目里最高的一级；全部落地写 `—`。
- `对外规格`：未纳入。`方案文档`：原文对应的方案路径（仓库内相对路径），没有写 `—`。`现状快照`：快照日期或 `—`。
- 待确认项写进「约束与说明」，项名写「待确认」。

**更新已有需求**

- 追加子编号：取该 R 现有最大子编号 +1，不重排。
- 改已有子编号：原地改，修订记录写「订正 RNN.k」。
- 删除条目：不删行，在需求列前加「（作废 YYYY-MM-DD）」。
- 已落地的 R 加了未完成条目：`status` 改为部分落地，`priority` 改为未完成条目里最高的一级。
- 现状快照只在原文是测评结果或实现说明时更新，日期同步 frontmatter。

**新建体系（存放路径下没有）**

成体系：把 `模板目录/成体系/` 整个复制到存放路径（`Copy-Item -Recurse`），得到 `README.md`、`需求分析/`、`需求规格说明书/`，然后：

1. 所有 `【系统名称】` 换成系统名。原文没有系统名就在第 4 步问。
2. `需求分析/需求/` 下按第 4 步清单新建 R01 起的文件，保留 `_模板-需求条目.md` 作后续模板。
3. 指向示例 `R01-需求名称.md` 的链接（总览、backlog、需求概览里都有）改成真实文件，示例台账行删掉，台账由第 7 步重建。
4. 总览：范围、核心流程、典型场景、非功能按原文写；没有依据的行删掉。
5. 通用规格：原文涉及才填。不涉及的文件删除，同时删总览「通用规格」表和 `通用规格/README.md` 里的对应行。`用语与优先级.md` 保留，只填实施分段名，原文没有就删掉那一行。
6. 需求概览：原文给了背景、分期、双方边界才填；单元格没依据写「待补充」，整行没依据就删行。
7. 术语表、案例库、backlog、修订记录按原文填；修订记录首行「建立需求分析」。
8. `需求规格说明书/` 原样保留，那是定版用的骨架。

单文件：复制 `模板目录/单文件/需求规范.md` 为 `<存放路径>/<系统名称>-需求规范.md`（存放路径以 `.md` 结尾就用那个文件名），按节填。每条需求写在第 9 节，第 8 节台账手工同步，修订记录写 0.1 节。没内容的节整节删，但第 8、9 节和 0.1 节必须保留。

### 6. 同步关联文件

| 文件 | 何时改 |
|------|--------|
| 总览台账 | 每次。成体系由第 7 步脚本重建，不手改；单文件手改第 8 节 |
| 修订记录 | 每次。倒序置顶，日期当天，「需求」栏写 R 编号或被改的子编号 |
| backlog | 有未完成条目时挂到 R 编号；全部落地的挪到已完成 |
| 通用规格 | 新增或修改了跨需求口径。新文件的编号前缀不得与已有前缀重复（scan 列出了已用前缀），并在通用规格 README 和总览补索引行 |
| 术语表 | 原文带来新产品名或新叫法，同时写「不要写成」 |
| 案例库 | 原文是问题、缺陷，或测评未通过 |
| 总览「核心流程」「典型场景」「非功能」 | 新 R 改变主流程、构成典型场景，或带了性能、安全等指标 |
| 总览「相关文档索引」、方案文档头部「关联需求」 | 原文对应一份方案或研究文档 |
| 需求概览「完成度对照」 | 体系里有需求概览，且新增了 R 或测评改变了完成度 |

已有体系缺其中某个文件（例如没有需求概览）时跳过，不为此新建。

### 7. 校验

动手前先跑一次校验记下基线：已有体系里可能本来就有与本次无关的 FAIL。收尾要求不新增 FAIL，且本次改动的文件没有 FAIL。

项目专属说明指定了校验命令时用它。否则：

```powershell
python .cursor/skills/requirement-breakdown/scripts/req_tool.py check <存放路径> --fix-index
```

`--fix-index` 按 frontmatter 重建成体系台账。「残留模板占位」的 WARN 逐个清掉（`需求规格说明书/` 下的骨架不报）。

写文件用 Write / StrReplace 工具。Windows 上必须用 PowerShell 写时用 `[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($false)))`，不要用 `Add-Content` / `Out-File`（会按 GBK 或带 BOM 落盘）。PowerShell 5 里命令间用 `;`。

### 8. 汇报

第一句给结论：写到哪套体系，新建了哪几条、更新了哪几条。然后列改动的文件，最后列推定的优先级、仍待确认的问题和未决冲突。分解清单放在汇报里，方便用户对照原文。
